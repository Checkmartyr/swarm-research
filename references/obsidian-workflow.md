# Obsidian storage and progress

Use this reference for destination selection, checkpoints, exports, and resumption. Research content schemas remain in [output-contracts.md](output-contracts.md); budget accounting remains in [research-protocol.md](research-protocol.md).

## Defaults and authority

- Vault disk root: `D:\obsidian_vault\Obsidian_vault`.
- Vault-relative research root: `Research/swarm-research`.
- Dashboard: `Research/swarm-research/dashboard.md`.
- Investigation folder: `Research/swarm-research/YYYY-MM-DD-<topic>` using the user's local date. Add `-2`, `-3`, etc. for new-run collisions. Generate one UUID `run_id` per investigation; preserve it on resume.
- Obsidian is authoritative after a verified checkpoint. Output copies are replaceable exports. Uncommitted new findings live in a pending local checkpoint and must be reconciled, not discarded because the vault is older.

Explicit user destinations override these defaults. All vault operations belong to the coordinator. Host Plan Mode permits only read-only discovery and planning; create no notes, metadata, exports, or checkpoints there. An explicit plan-only request has no research execution and saves its plan only when requested and permitted.

## Discover and verify the connection

1. Discover actual Obsidian MCP tools and their schemas. Use a read-only root listing and read known existing content. Merely having a tool registered does not prove connectivity.
2. Bind MCP to the requested disk vault by comparing normalized content at `SCHEMA.md` and a distinctive existing note, together with their relative paths and root listing. Record the selected paths, content hashes, MCP tool/server identity, and resolved disk root in the local checkpoint binding. Never expose credentials or read plugin secrets to establish this binding.
3. If disk access is unavailable, a previous verified binding plus matching `run_id` and managed note content at the recorded MCP paths can reestablish identity. A matching vault display name alone is insufficient. Without a reliable binding, keep writes local/pending and explain the unresolved destination; ask for confirmation only if needed to proceed.
4. If MCP is missing, unreachable, targets a different vault, or lacks necessary safe create/update/read operations, use the specified disk vault if it is accessible and authorized. A mismatch is not permission to modify the other MCP vault. Request normal host filesystem access when required. Explicit permission denials must be honored rather than bypassed through another route.

The inspected MCP exposes `obsidian_list_files_in_vault`, `obsidian_get_file_contents`, `obsidian_append_content`, and `obsidian_patch_content`; discover their current namespace and schemas rather than assuming these names always exist. The append tool can create notes, but also appends to existing ones: an absence check alone is not safe creation. Require an exclusive-create/conditional-create capability for missing notes; if the adapter lacks it, choose authorized disk fallback and create files exclusively, failing on existence. On disk, reserve a new run directory exclusively and retry the numeric suffix on collision. For a dashboard creation collision, reread and verify ownership before merging into it. Never append a complete document into an existing file. Use targeted replacement of an owned heading or frontmatter field for updates. Avoid delete-and-recreate updates. If required parents or patch operations are unsupported, choose disk fallback instead of guessing tool behavior.

Pin the chosen route for each checkpoint. After falling back to disk, use disk for the rest of that run. Recheck MCP at a new invocation/resumption; a return to MCP must read the same committed run first. Do not dual-write through MCP and disk as if they were separate destinations.

Serialize cooperating coordinators before reading bases or changing shared notes. With authorized disk access, exclusively create `Research/swarm-research/.swarm-write.lock` containing a unique holder token, invocation identity, and timestamp; hold it for the checkpoint including dashboard update, then remove only the lock still bearing that token. A known live holder means save pending until released. A leftover lock may be removed only after confirming its holder stopped; otherwise report it pending instead of stealing the lock. Check containment for the lock path too. When disk locking is unavailable, use advertised server conditional writes for both note creation and updates; if neither mechanism is available, retain pending work rather than racing another coordinator. The lock protects only cooperating writers: still compare actual content immediately before changes to catch user edits, and disclose that an adapter without conditional writes cannot eliminate the final read/write race.

## Paths, schema, and ownership

Inspect applicable vault instructions and `SCHEMA.md` before creating notes. This vault requires lowercase-kebab-case filenames, YAML `title`, `created`, `updated`, `type`, `tags`, `sources`, at least two outbound wikilinks per note, and callouts for summaries or contradictions. It requests splitting pages beyond 250 lines. It specifies no enumerated type values or date format; default to `research-plan`, `research-evidence`, `research-report`, `research-dashboard`, and `research-part`, with ISO 8601 timestamps including the user's local UTC offset. Keep `created` fixed; update `updated` on saves. Quote/serialize YAML values correctly and use lists for tags/sources. Do not add an empty source or invent a citation to populate metadata.

Use `research` tags, plus `meta` for plan/dashboard and relevant existing topic tags. Link each project note to at least two actual companion notes; child notes can link to their root and the plan. A dashboard with one investigation links its plan and report. When no investigation exists, defer dashboard creation. Use `> [!ABSTRACT]` for the report summary and `> [!WARNING]` for material contradictions/pending-save notices when appropriate.

Validate every disk destination before creating or changing it. Accept only vault-relative paths constructed from safe slugs. Reject absolute/drive-qualified topic paths, `..`, alternate-data-stream colons, Windows reserved device basenames, and trailing spaces/dots. Resolve the real vault root and existing parent components; reject symlinks/junctions that escape it. Enforce containment using path components, not a string prefix. Scope changes to this skill's run folder/dashboard and explicit user-authorized destinations; never alter vault configuration or unrelated notes.

On creation add `swarm_owner: swarm-research`, `run_id` (project notes), `checkpoint_revision`, and `research_status` to frontmatter. These fields and the required metadata above are skill-owned, but manually edited values still require conflict handling. The plan also owns its persistence fields; other user-added keys are preserved. The dashboard uses `swarm_owner` but no single run ID or project revision; each row carries its own run ID/revision.

Give each generated note a unique top-level `# Swarm Research` section for managed content and a sibling `# Personal Notes` section for user content. Descendants of the managed section are skill-maintained; user changes inside it count as conflicts, not disposable text. Patch only that section and explicitly owned frontmatter keys. Re-read/compare owned fields and managed content immediately before every update. Preserve all content outside those regions.

Never adopt an existing note solely because its path matches. A project file must have the expected owner/run ID. For a new run, choose another folder if any project files collide. If the default dashboard exists without this owner, use the next available `dashboard-2.md`, etc., and persist that path. During resumption, unexpected ownership is a conflict; preserve pending work rather than silently switching projects.

## Checkpoint and progress protocol

Research status and save status are separate. Use research states `pending`, `running`, `review`, `complete`, `partial`, `blocked`, `cancelled`. Save state is `saved`, `pending`, or `conflict`; dashboard/export freshness is tracked separately. The dashboard shows one row per `run_id`: project links, research state, completed/total task count, assignments used/limit, latest timestamp, blocker, and committed revision. Derive counts from the plan; do not infer completion from agent termination.

At initialization create the plan, a ledger with no invented evidence, and a report explicitly marked pending. Register the dashboard only once project notes can be read. Use the following protocol at initialization, task dispatch/completion, after waves, during review, and at completion/interruption:

1. Read current project notes and the dashboard. Reconcile prior incomplete revisions first. Record base managed-content hashes and preserve existing personal sections/unknown metadata.
2. Build the next revision locally under `work/<run-id>/pending/`: exact base and intended Markdown snapshots plus a manifest with run ID, vault binding, relative paths, prior/new revisions, hashes of the managed sections and owned fields, task/budget snapshot, and desired dashboard row. Include base text and owned metadata, not only hashes, so interrupted merges can compare all three versions. Keep this durable pending copy until the checkpoint and derived outputs verify successfully.
3. Write child notes, evidence, and report; then verify their contents and revision by reading them back. Use compare-and-set/conditional writes when offered. Otherwise re-read immediately before each replacement and compare with the base. For disk, stage a temporary file in the same directory and use an atomic replace after that comparison. This reduces but does not eliminate races on backends without conditional writes; never claim transactional guarantees there.
4. Commit the plan last among project notes, with the new revision and a manifest of the other managed-note hashes. Read it back and verify the full project snapshot. Exclude the plan's own hash from its embedded manifest; keep that hash in the local checkpoint. If any project operation fails, leave the local save state pending/conflict and retain the manifest for repair.
5. Upsert the dashboard row by `run_id`, preserving other rows and personal content. Verify it. Regenerate local exports from the confirmed project snapshot and verify links and revision. If either derived operation fails, the project checkpoint is saved but dashboard/exports are explicitly stale; do not undo successful project saves or label the whole delivery fully synchronized.

MCP patches may need multiple calls per note. Readback must verify both frontmatter and managed content before counting that note as saved. When updating the dashboard, re-read immediately before merging rows and guard against concurrent changes just as for project notes.

Record `hash_scheme: sha256-utf8-lf-v1` in checkpoint manifests. Hash managed text as UTF-8 without BOM with CRLF/CR normalized to LF and no trimming. Hash owned metadata as compact JSON with recursively sorted object keys, preserved array order, literal Unicode, and quoted ISO timestamps; exclude user-owned keys. Use the same convention for verification and resume, while retaining exact base snapshots for merges. If resuming an older manifest with another or missing convention, compare its base/target snapshots directly and migrate the manifest only after verifying their content; do not assume a hash mismatch proves an edit.

## Failures and recovery

- **Uncertain write/timeout:** read the destination via the active route, or the verified same-vault disk fallback. If it equals the intended content/revision, count that write as succeeded. If it equals the base, retry only once through the selected available route. For partial/different content, reconcile against base and intended snapshots; do not blindly append or replace. If neither route can read, leave pending.
- **Concurrent edits:** merge only demonstrably nonoverlapping edits, preserving personal sections and unknown keys. If managed text or owned metadata changed ambiguously, save the intended version locally as conflict material and report the affected note/section. Keep existing content untouched until resolved.
- **Partial revision:** on resume compare the plan manifest, actual project notes, and durable pending manifest. Finish an interrupted intended revision only when base/target comparisons are safe. Without enough evidence, retain it as pending/conflict rather than trusting a mixed snapshot or rolling files back. Rebuild dashboard and exports after reconciliation; preserve budget consumption and stable IDs.
- **Both routes blocked:** keep research outputs and state locally marked pending-save. Continue permitted research, but retry saving only after an access condition changes or the user requests it. At closure clearly distinguish completed research from unsaved vault results.

Store failure detail and active route in local pending state when the vault cannot be updated. Do not claim that an unchanged vault note records a failure it could not receive. Keep old verified exports available, and place newer unsaved results under a clearly labeled `pending` output subfolder if the user needs them before synchronization.

## Splitting notes and local exports

When a managed note would exceed 250 lines, move full sections/claims/sources into numbered child notes with required metadata and companion links. Keep root indexes and stable claim/source headings and anchors so existing links still resolve. A moved entry's root stub links to its child and the child links back. If the root exceeds the limit because of stable link stubs or user-owned content alone, retain those links/content, document the exception, and avoid deleting anchors or splitting personal text without user direction.

Export the three roots and every referenced child note from the same confirmed checkpoint. Retain run ID, revision, provenance, and source URLs. Convert internal wikilinks, aliases, and heading links to relative Markdown links and portable anchors. When the plan links the dashboard, include a dashboard snapshot in a sibling export location and rewrite known rows to existing local exports; for other rows use supported vault/file links rather than inventing local copies. For links to existing external-to-run vault notes, use their verified absolute file paths when the host supports them; otherwise retain the vault reference visibly, without pretending it is a local file. No private note content needs copying merely to satisfy a link.

The final response links the three local root exports, gives the vault-relative folder/dashboard location, and states any pending/conflict or stale-derived state. Resume from authoritative vault notes plus pending checkpoints, never from an export alone when newer vault state exists.
